## 1. 目标、范围与默认决策

### 1.1 产品目标

以 FC 时代《坦克大战》的视觉与核心玩法为参考，实现固定屏幕、四方向移动、保护基地、可破坏砖墙及敌军波次的 2D 游戏。

首版追求经典观感和操作体验，不承诺模拟器级、逐帧一致的原版复现。未经确认的原版数值和规则应记录为待校准项，不直接作为既定事实。

### 1.2 首版范围

| 项目 | 默认方案 |
| --- | --- |
| 目标平台 | Windows 桌面 |
| 首版模式 | 单人 |
| 输入 | WASD / 方向键移动，Space 射击；暂停键在输入配置中明确 |
| 地图 | 先完成第一关，再扩展数据驱动的多关卡 |
| 画面 | FC 风格，固定画面，整数倍缩放和黑边 |
| 必须包含 | 移动、射击、砖墙破坏、敌军、基地、生命、复活、胜负、重开 |
| 后续经典内容 | 敌人类型、升级、道具、特殊地形、计分、完整流程、音频 |
| 首版不包含 | 网络联机、移动端、复杂寻路、现代光照与后处理 |

本地双人、手柄、关卡编辑器属于可选扩展，不作为单人版本完成的前置条件。

## 2. 技术路线与约束

### 2.1 像素与显示

- 以 **256 × 240** 为参考画面，以 **208 × 208** 为地图游戏区的规划起点。
- PPU 暂定 **16**，16 × 16 像素坦克约对应 1 Unity 单位。
- 采用 URP 自带的 `UnityEngine.Rendering.Universal.PixelPerfectCamera`，不安装 Built-in 专用的 Pixel Perfect 包。
- Point 过滤、关闭纹理压缩与 Mip Maps；关闭影响像素边缘的抗锯齿和后处理。
- 优先使用 Unlit Sprite 材质，避免改变素材颜色。
- 在阶段 0 校验实际素材尺寸、地图边距与 HUD 布局后冻结规范。
- 相机参考分辨率、Tilemap 原点、Sprite Pivot 和地图坐标转换统一记录，不在各脚本中分别猜测。

### 2.2 地图模型

- 地图数据负责阻挡、破坏和查询；Tilemap 负责显示。
- 16 × 16 像素用于大格和关卡布局；8 × 8 像素用于小地形及转向对齐参考；4 × 4 像素作为砖墙细分破坏的规划粒度。
- 上述粒度需要通过通道、坦克占地和墙体破坏试验验证后确定，不强制所有显示 Tile 都使用同一尺寸。
- 分离地表、障碍、草丛遮挡和动态对象。
- 地图变化先修改唯一的逻辑数据源，再更新显示，不以 Tile 是否可见作为碰撞真相。
- 不为每个砖墙碎片建立独立 GameObject。

### 2.3 移动、战斗和更新顺序

- 优先采用固定逻辑步长、自定义网格查询、坦克矩形碰撞和子弹扫掠检测。
- 移动连续进行，不是逐格跳跃；转向和通道对齐参照网格。
- 不使用动态刚体推动坦克，不同时维护相互矛盾的物理与网格碰撞状态。
- 玩家与敌人复用坦克移动、武器、受击、死亡和动画能力，只替换控制来源。
- 敌人使用轻量状态机、方向权重和遇阻转向，不先引入 NavMesh 或全知最短路径算法。
- 逻辑时间、暂停时间、道具时间统一管理；规定同一步内的输入、移动、碰撞、伤害、死亡及胜负判定顺序。
- 对象池按需要用于子弹、爆炸等高频对象，不提前引入大型框架。

### 2.4 数据、界面与工具

- 关卡、坦克参数、波次和 Sprite 映射采用可校验的数据资产；具体格式在阶段 0 确定。
- 游戏逻辑尽量不依赖场景对象，便于 EditMode 测试。
- UI 默认采用 uGUI，图标与位图数字优先保持像素风格。
- 通过 Unity CLI 和编辑器 API 修改场景、Prefab、Importer 等资源；不手写 `.unity`、`.prefab` 或 Sprite `.meta` 内容。
- 仅修改任务范围内的资源；切图前保留原始素材和可回退点。

## 6. 测试与阶段完成标准

### 6.1 各层测试

| 层级 | 重点 |
| --- | --- |
| EditMode | 坐标转换、边界、地图查询、扫掠命中顺序、砖墙破坏、伤害与分数、波次和胜负规则 |
| PlayMode | 输入到坦克行为、场景绑定、生成回收、复活、暂停、UI 更新、完整重开 |
| 人工体验 | 转向与贴墙、射击节奏、敌人行为、像素对齐、画面缩放、音频反馈 |
| 独立构建 | 真实窗口输入与焦点、保存、分辨率、连续游戏、退出及运行日志 |

关键回归案例：

1. 贴墙转向、交叉路口与窄通道不穿墙。
2. 子弹跨越多个破坏单元时只处理正确的首个阻挡目标。
3. 残墙的显示、子弹阻挡和坦克通行结果一致。
4. 出生点被占用时不会生成重叠坦克或丢失波次。
5. 玩家受击、复活保护和生命耗尽只结算一次。
6. 基地毁坏与最后敌人死亡同一步发生时，胜负结果固定。
7. 暂停不消耗战斗计时；恢复后不突然补算大量移动或射击。
8. 连续重开不残留子弹、敌人、道具、事件订阅和延迟回调。
9. 30/60/144 渲染帧率下，相同逻辑输入得到一致的移动距离和冷却结果。
10. 失去窗口焦点后按明确策略暂停或继续，不因编辑器冻结误判游戏运行正常。

### 6.2 通用完成定义（DoD）

任务完成至少应满足：

- 交付物已保存，引用完整，职责符合约定。
- 对应自动测试或人工步骤已执行，记录结果与未覆盖项。
- 无新增编译错误和 Console 错误；新增警告需要说明并处理。
- 不留下临时验证代码、无用途日志或测试对象。
- 涉及运行行为时，确认游戏确实推进，而不只是进入了 Play Mode。
- 更新任务复选框、当前看板和实施记录；有版本控制时关联提交或回退点。

阶段里程碑只有在本阶段所有必选任务完成、阶段验收通过后才可标为完成。

## 7. Unity Skills 与 CLI 的使用约定

| 工作 | 主要工具或 Skill |
| --- | --- |
| 编辑器连接、命令发现、运行状态与 Console | `unity-cli` |
| Sprite 切分、Rect、Pivot | `sprite-editor` |
| URP 像素相机与清晰度 | `2d-pixel-perfect` |
| Tile Palette / Tilemap 辅助工作流 | 按需使用 `create-tile-palette-or-rule-tiles` |
| HUD 与菜单 | `ui` → `ui-ugui` |
| 音频路由与优化 | 按需使用音频相关 Skills |

实施流程：

1. 读取当前任务对应的 Skill，检查目标工程和编辑器连接。
2. 从实际命令目录发现命令名称和参数，不依赖旧示例中的命令名称。
3. 通过编辑器 API 创建或修改资源，源代码通过文件编辑工具维护。
4. 检查编译与 Console，再执行目标测试和运行验证。
5. 保存资源并更新文档，不将工具安装成功视为游戏功能完成。

## 8. 风险、待确认项与处理策略

| 项目 | 风险或未决内容 | 处理方式 |
| --- | --- | --- |
| 素材使用权 | 现有图集与原作内容可能受版权约束 | 学习原型与公开发行分开处理；公开发布前确认授权，必要时替换原创素材 |

| 音频来源 | 当前精灵图不能提供音频 | BC-403 单独准备并确认使用条件 |
| AI 与物理复杂度 | 过早引入复杂寻路或多套碰撞会增加返工 | 固定逻辑更新和单一碰撞真相，先做简单可复现 AI |
| 范围膨胀 | 双人、编辑器和移动端拖延单人闭环 | 严格以 M2 为首个交付点，可选扩展独立排期 |
